# Phase 3 — Windows destructive-operation safeguards
Objective: Add opt-in, project-local pre-execution security hooks for Codex and OpenCode that conservatively detect dangerous file deletion and destructive SQL operations on Windows.
Branch: `codex/phase-1-tui` (preserve the existing dirty worktree; no commits that capture unrelated Phase 0/1/2 changes).
Delivery: `ask-on-risk`; forecast approximately 700 authored lines. Test runner: `npm test`, `npm run typecheck`, and `npm run build`.

## Specs
1. **S1 — Threat model and shell scope.** Roadmap: "Define the threat model and supported hook events for each agent adapter." User selected: "Powershell. cmd y git bash". Cover PowerShell, cmd.exe, and Git Bash/MSYS on Windows for pre-execution checks only. Hooks are advisory defenses, not a sandbox: shell obfuscation, encoded payloads, scripts, aliases/functions, alternate executables, direct database/API use, and unrecognized syntax may evade detection. Document exactly what is recognized, blocked, passed through, or unsupported. Do not claim comprehensive prevention.
2. **S2 — Pre-execution adapter contracts.** Codex uses its supported pre-tool hook event; OpenCode supports both the V1 `tool.execute.before` plugin API and V2 `ctx.tool.hook("execute.before", ...)` plugin API through distinct entrypoints. Keep native event/config translation in separate adapters and share a typed policy decision engine. Only install project-local files/config entries; preserve user-owned entries and never modify global configuration. Runtime/event failures must not be represented as a successful block; unsupported event payloads must be reported distinctly.
3. **S3 — Conservative destructive-operation policy.** Roadmap: "Add safeguards for abusive or accidental file deletion commands and destructive SQL operations affecting objects or data." Parse supported shell command structures and quoting/wrappers into structured invocations; do not use substring-only matching. Deny high-confidence dangerous recursive/broad filesystem deletion targets and high-confidence destructive SQL (DROP, TRUNCATE, and unscoped DELETE/UPDATE); explain the matched command, rule, and reason. Pass through harmless near-matches. Where syntax cannot be safely classified, return an explicit unsupported/indeterminate decision rather than silently claiming protection.
4. **S4 — Safe user workflow and opt-in.** Roadmap: "Explain each block, provide a safe confirmation/escalation path where appropriate, and keep hook enablement visible in the TUI." Roadmap: "Keep hook installation opt-in until its behavior and platform coverage are demonstrated." Show hook state in the TUI and require explicit project-local installation/enablement. A block must explain how the user can inspect/change the command and re-submit; no hidden auto-approval or global bypass.
5. **S5 — Coverage and limits.** Roadmap: "Test direct commands, common shell wrappers, quoting/escaping, harmless near-matches, and unsupported shell/event behavior." Add deterministic tests for PowerShell, cmd.exe, Git Bash/MSYS, SQL cases, wrappers, quoting/escaping, benign near-matches, malformed/unrecognized syntax, and native adapter block/pass-through/failure mappings. Use isolated temporary projects and preserve pre-existing settings.
